# 计算资源降本：选型、RightSize 与计费模式（含 x86/ARM 对比）

> 计算资源是云成本的大头（EC2 相关往往占 40%+）。本文覆盖完整降本链路：实例选型 → RightSize → 计费模式（On-Demand / SP / RI / Spot）→ 架构迁移（x86 → Graviton/ARM）。

## 一、实例家族与规格选型

AWS EC2 实例按用途分族，选错家族是隐性浪费的常见来源：

| 家族 | 侧重 | 典型场景 |
| --- | --- | --- |
| M 系（通用） | CPU/内存均衡 | Web/应用服务器、中小数据库 |
| C 系（计算） | 高 CPU | 批处理、渲染、数据处理 |
| R/X 系（内存） | 大内存 | 缓存、内存数据库、分析 |
| I/D 系（存储） | 高 IO/大容量本地盘 | 数据库、日志、缓存节点 |
| G/P/T 系（GPU） | 图形/推理/训练 | 机器学习、渲染 |
| T 系（突发） | 可突发的低配基线 | 开发测试、低负载长尾服务 |

**选型原则**：先按负载特征选族（CPU/内存/IO 比例），再按规模选规格；不要用高配通用实例硬扛特殊负载。

同一家族内按大小阶梯（如 `m6i.large → xlarge → 2xlarge → 4xlarge → 8xlarge → 12xlarge`），每档 CPU/内存翻倍、成本约翻倍。降一档规格（如 12xlarge → 8xlarge）约省 1/3 成本。

## 二、RightSize（降配）方法论

### 数据先行

- 采集 1-3 个月 CloudWatch 指标：CPU、内存、网络、磁盘 IO。
- **不要只看平均值**：结合 P95/P99 与业务峰值判断；平均值低但峰值打满的实例不能直接降配。

### 判断标准

| 观察项 | 降配信号 | 谨慎信号 |
| --- | --- | --- |
| CPU 利用率 | 持续 < 30%（核心）/ < 20%（非核心） | 有周期性峰值、批量任务时段 |
| 内存利用率 | 持续 < 40% 且无增长趋势 | 内存增长趋势明显（疑似泄漏） |
| 网络/IO | 长期低水位 | 大促/版本发布前 |

### 执行步骤

1. 建立利用率基线报告（含峰值）。
2. 按「非核心 → 核心」顺序推进，先小后大。
3. 降配前备份实例配置/快照，记录原规格以便回滚。
4. 降配后持续监控 1-2 周，对比业务指标，异常则回滚/扩容。
5. 保留扩容预案：RightSize 不等于锁死规格，配合自动伸缩应对突发。

### 业务分层策略

| 分层 | 策略 |
| --- | --- |
| 核心业务 | RightSize 谨慎评估；长期稳定负载配 SP/RI；保留按需余量 |
| 非核心业务 | 优先 Spot + 自动启停（夜间/节假日）；RightSize 激进些 |
| 测试环境 | 自动销毁（如 7 天无活动）；最小规格/Spot/共享账号 |

## 三、计费模式：On-Demand / SP / RI / Spot

| 模式 | 折扣 | 灵活性 | 适用 |
| --- | --- | --- | --- |
| On-Demand（按需） | 0% | 最高 | 短时/波动/测试 |
| Compute Savings Plans | 最高约 66% | 高（EC2 + Lambda + Fargate） | 跨服务混合负载 |
| EC2 Instance SP | 最高约 72% | 中（限定实例族/区域，族内 Size Flex） | 单一实例族稳定负载 |
| Standard RI | 最高约 72%（3 年全预付） | 低-中（族内 Size Flex） | 长期固定配置 |
| Convertible RI | 约 54-66% | 中（可等价更换族/规格） | 架构演进期 |
| Spot | 最高约 90% | 极高（可被回收） | 可中断、无状态任务 |

### 选择决策

```text
负载是否长期稳定？
├─ 是：
│   ├─ 跨多个实例族/服务 → Compute SP（省心）
│   └─ 单实例族为主 → EC2 Instance SP 或 Standard RI（折扣更深）
├─ 否（架构可能变）：Convertible RI 或 SP（保灵活性）
└─ 可中断/无状态 → 直接考虑 Spot
```

### 采购策略（避坑）

1. **先 RightSize 再买**：按降配后的真实用量采购，避免「买完发现规格买大了」。
2. **期限**：1 年灵活但折扣浅；3 年折扣深（最多差约 10 个百分点），确认长期稳定再选 3 年。
3. **付款方式**：全预付折扣最高、部分预付次之、无预付最低；按现金流选择，别为了折扣占压资金。
4. **覆盖匹配**：定期核查 RI/SP 覆盖与实际运行实例的匹配度，未覆盖 = 浪费折扣，覆盖过度 = 浪费承诺。
5. **Size Flex**：EC2 Instance SP / Standard RI 支持族内规格弹性，按族而不是按单一规格规划。
6. **三层组合**：RI/SP 覆盖基线，按需覆盖峰值，Spot 覆盖可中断负载，通常最优。

## 四、Spot 实例专项

### 核心概念

- AWS 将闲置容量以折扣价出售，**最高可省约 90%**；阿里云对应「抢占式实例」。
- 容量被回收时提前约 **2 分钟**通知，实例会被停止/终止。

### 适用 / 不适用

| 适合 | 不适合 |
| --- | --- |
| 无状态批处理、CI/CD 构建 | 数据库主节点 |
| 大数据/机器学习训练（可断点续跑） | 有状态长连接服务 |
| 测试/预发环境 | 强 SLA 在线核心链路 |
| 弹性扩容的 Worker 节点 | 本地盘有持久数据的服务 |

### 最佳实践

1. **多样化实例池**：≥10 种实例类型、≥3 个可用区。
2. **用 Auto Scaling Group**，不要用独立 Spot 请求；配 On-Demand 兜底比例。
3. **假设随时会被回收**：任务状态写外部存储（S3/OSS），支持断点续跑；捕获中断信号做优雅退出。
4. **分配策略用 `price-capacity-optimized`**（兼顾价格与容量可用性），不要手动调低价格上限。
5. **Spot 只放弹性层**：基线用 RI/SP，峰值与可中断任务用 Spot。
6. **监控中断率**：用 Spot Advisor 选中断率低的实例类型。

## 五、x86 vs ARM（Graviton）价格对比与迁移

### 差距在哪里

- Graviton（ARM）同规格实例**列表价约低 20%**，性价比最高提升约 40%（官方口径）。
- 对多数云原生负载（Web、微服务、容器、数据库 OLTP、数据分析），性能不降反升。

### 价格对比（示意，以官方定价页为准）

| 对比项 | x86（如 m6i.large） | Graviton（如 m6g.large） |
| --- | --- | --- |
| 按需列表价 | ~$0.096/h | ~$0.077/h（约低 20%） |
| 3 年全预付 RI 后 | ~$0.027/h | ~$0.022/h |
| 性价比（官方口径） | 基线 | 最高 +40% |

### 适用评估

- **高适配**：容器化/无状态微服务（多平台镜像）、Web/API、数据库（RDS Graviton）、缓存（ElastiCache Graviton）、数据分析、CI/CD。
- **需谨慎**：依赖 x86 指令集/闭源二进制、旧版 Oracle/专有软件、未适配 ARM 的第三方库。

### 迁移方法论

```text
1. 盘点：梳理运行在 x86 的实例/服务清单
2. 兼容性评估：镜像多平台构建、依赖库 ARM 支持
3. 压测对比：同负载下 x86 vs Graviton 的延迟/吞吐/成本
4. 试点：先迁非核心服务，灰度验证业务指标
5. 推广：逐步迁移，配合 RI/SP 采购锁定折扣
6. 复盘：对比迁移前后成本与性能
```

**关键提醒**：

- 迁移与 RI 叠加：先迁 Graviton 再买 RI（或买 Graviton 的 RI），把「列表价低 20%」与「RI 折扣」叠加。
- 镜像必须多平台构建（`docker buildx` 或 CI 多架构流水线）。
- 数据库迁移先跑兼容性测试与性能基准，再切流量。

## 六、CPU 代际升级：性能红利与旧代际的隐形成本

### 为什么代际重要

云厂商持续换代 CPU（如 AWS x86 实例 m5 → m6i → m7i，Intel/AMD 新代际；以及 Graviton 1/2/3/4 逐代演进）。新代际在**同规格下 IPC、主频、内存带宽、网络与存储能力**普遍更强，而定价通常持平或略涨——这意味着「性能/价格」显著提升，是比单纯降配更值得关注的成本红利。

### 代际差异带来的提升

- **同规格性能更强**：相同负载在新代际上 CPU 占用更低、P99 延迟更低、吞吐更高。
- **等价降规格**：旧代际需要 4C 的负载，新代际可能 2C 即可满足 → 规格下降 + 单价相近 = 单位成本大幅下降。
- **特性升级**：新实例往往带更优的网络（如 Nitro/ENA 增强）、存储 IO、安全特性。

### 示例测算（示意，以实际压测为准）

假设某服务在 m5.xlarge（旧代际）CPU 持续 70%：

| 方案 | 规格 | CPU 占用（同负载） | 成本 |
| --- | --- | --- | --- |
| 维持 m5.xlarge | 4C16G | ~70% | 基线 |
| 升级 m7i.xlarge（同规格） | 4C16G | ~45% | 持平或略高 |
| 升级 + 降档 m7i.large | 2C8G | ~90%（仍有余量） | 约省一半 |

> 性能数据必须来自同负载压测；不同业务特征（CPU 密集/内存密集/IO 密集）收益差异大。

### 旧代际的隐形成本（容易被忽略）

| 隐形成本 | 说明 |
| --- | --- |
| 性能瓶颈 | 旧代际同规格性能低，为达到 SLA 需要更多实例/更高规格 → 隐藏的额外成本 |
| 延迟偏高 | 影响用户体验，可能间接造成业务损失 |
| 能耗与密度 | 每单位算力耗电更高，物理机成本与碳排放更高 |
| 功能缺失 | 新指令集、网络/存储特性（Nitro、ENA、高带宽）不可用 |
| EOL / 支持风险 | 实例类型淘汰后被动强制迁移，一次性成本更高、时间不可控 |
| 迁移测试成本 | 升级本身要压测、试点、验证，属于一次性投入，需摊薄到收益里评估 |

### 升级方法论

```text
1. 盘点：列出旧代际实例清单（类型/规格/用途/CPU 占用基线）
2. 压测对比：同负载下新旧代际的 CPU、内存、网络、P50/P99 延迟
3. 等价映射：按实测性能确定新代际规格（可能直接降一档）
4. 试点：非核心服务先迁，验证业务指标与稳定性
5. 推广 + 联动计费：确认稳定后按新规格采购 SP/RI 锁定折扣
6. 复盘：对比升级前后的成本、性能与稳定性
```

### 注意事项

- **兼容性**：依赖特定 CPU 指令集或按核收费的许可（如部分商业数据库）需先评估。
- **特性差异**：新实例网络拓扑/挂载方式可能变化，需重新确认安全组、存储与监控。
- **顺序**：先 RightSize 看基线，再谈代际升级；小规格试点，不要全量一把切。
- **时间窗口**：结合实例类型 EOL 时间主动规划升级，避免被动迁移。
- **与 RI/SP 联动**：新代际买 RI 前先完成等价规格确认，避免「买完又发现规格不对」。
