# 数据生命周期降本方法论

> 核心思想：**数据价值随时间衰减，存储成本也应随之下降**。通过「删除、压缩、分层、归档」四个动作，让数据在正确的时间、待在正确的存储层。

## 一、核心思路

数据成本 = 存储单价 × 数据量 × 保留时长。降本可以从三个变量同时下手：

| 变量 | 手段 |
| --- | --- |
| 单价 | 热数据放贵存储、冷数据放便宜存储（分层） |
| 数据量 | 清理无效/重复数据、压缩、分区裁剪（减量） |
| 时长 | 按合规与业务要求设定保留期，到期自动删除（控期） |

四个基本动作：

1. **删除（Delete）**：无价值/超期数据直接删，最省。
2. **压缩（Compress）**：同一层内压缩，减少体积。
3. **分层（Tier）**：按访问频率迁移到更便宜层。
4. **归档（Archive）**：低频长期数据进归档存储。

## 二、通用方法论（五步）

### 1. 盘点数据资产

列出数据类型（数据库、快照、日志、文件、索引）、来源、增长速率、访问频率、合规保留要求。

### 2. 定义分层模型

为每类数据定义：热/温/冷/归档各层、每层保留周期、访问时效要求（毫秒/分钟/小时）。

### 3. 制定生命周期规则

用自动化规则落地分层与删除，避免靠人肉清理：

- 快照：快照生命周期策略
- ES：Index Lifecycle Management（ILM）
- S3/OSS：生命周期规则（按天转层 + 过期删除）
- 本地日志：logrotate 按大小/天数轮转

### 4. 成本测算

各层单价 × 数据量 × 保留时长，对比优化前后总成本；小对象、取回费、最低计费时长都要算进去。

### 5. 监控与复盘

成本看板跟踪各层用量与费用；季度复盘，按业务变化调整保留周期与分层边界。

## 三、示例 1：快照保留周期降本

### 问题

- 快照冗余、保留时间过长，快照费用持续上涨。
- 全量备份频率过高（如每 4 小时一次），备份存储量翻倍。

### 方案

1. **清理未使用快照**：先清冗余与孤儿快照（快照费用可能一次下降明显）。
2. **调整备份频率**：全量备份从 4 小时改为 8 小时，备份存储费约减半。
3. **分层保留**：
   - 近 3 个月：增量快照（常用恢复窗口）；
   - 年度：1 个全量快照（灾难恢复基线）；
   - 更久：迁移到对象存储归档类（Glacier/冷归档）。
4. **自动化**：配置快照生命周期规则，禁止手建手删。

### 检查点

- 保留周期与 RPO/RTO 匹配（恢复目标要求多久内的数据）。
- 核心业务必要快照范围确认，避免误删。
- 快照与备份（如 RDS 备份）双链路并存时的重复成本评估。

## 四、示例 2：RDS MySQL 大表归档至 S3

### 问题

- 大表持续增长，占用预置存储（如 gp2），存储单价高。
- 历史数据几乎不访问，却和热数据同样计费。

### 方案

```text
识别冷数据（按时间字段/访问频率）
  → 定期导出归档（CSV/Parquet 到 S3，或建归档库）
  → 原表按分区裁剪/删除
  → 需要时从 S3 取回或通过分析引擎查询
```

1. **冷数据识别**：按业务时间字段（如 `gmt_created`）和访问频率确定归档边界（如 1 年前）。
2. **归档导出**：定时任务导出到 S3（数据校验：行数、哈希）。
3. **删除策略**：先归档成功并校验，再分区删除；删除前双确认。
4. **查询方案**：归档后数据通过 S3 + 分析引擎（Athena/OSS 外表）查询，或按需取回。
5. **存储分层**：S3 内再按访问频率分层（见示例 4 的 S3 内分层）。

### 降本效果

高性能预置存储（如 gp2/ESSD）→ 低频/归档存储，存储单价差距可达 5-20 倍，随数据量增长收益放大。

### 注意事项

- 归档任务要可重试、幂等，避免重复导出或漏数据。
- 删除线上数据前必须完成校验与合规确认。
- 大表删除用分区裁剪/分批删除，避免大事务与锁。

## 五、示例 3：ES 冷热分层（日志场景）

### 架构

```text
热节点（hot）：SSD，近期日志，近实时查询
  → 温节点（warm）：大容量盘，稍旧日志
  → 冷阶段（cold）：冻结索引或归档
  → 到期删除 / 转存 S3
```

### ILM 配置思路

用 Index Lifecycle Management 自动流转：

```json
{
  "policy": {
    "phases": {
      "hot": {
        "actions": { "rollover": { "max_age": "1d", "max_size": "50gb" } }
      },
      "warm": {
        "min_age": "7d",
        "actions": { "allocate": { "require": { "data": "warm" } }, "force_merge": { "max_num_segments": 1 } }
      },
      "cold": {
        "min_age": "30d",
        "actions": { "searchable_snapshot": { "repository": "s3-repo" } }
      },
      "delete": {
        "min_age": "90d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

### 降本点

- 热数据只保留短窗口（如 7 天），SSD 用量大幅下降。
- 温/冷数据用大容量磁盘或可搜索快照（存 S3），存储单价低数倍。
- force_merge 减少分片与段开销；合理设置分片大小与副本数。

## 六、日志全链路分层方案（原始日志 → ES → S3 → 合规归档）

### 分层链路

```text
采集端日志（本地）
  → 原始日志本地保留（固定 GB 大小，如 10GB，超限轮转删除）
  → ES 热日志（保留 7 天，SSD，近实时查询）
  → ES 冷日志（保留 30 天，冷节点/冻结索引）
  → 合规日志（按合规要求保留 2 年）转存 S3
  → S3 内再分层：0-90 天 Standard-IA → 90 天+ Glacier → 1 年+ Deep Archive
  → 2 年到期按合规要求删除
```

### 各层明细

| 层级 | 存储 | 保留周期 | 访问时效 | 查询方式 | 成本特征 |
| --- | --- | --- | --- | --- | --- |
| 本地原始日志 | 节点磁盘 | 固定 GB（如 10GB）或 N 天 | 秒级（本机） | grep/tail | 占用节点盘，控制大小 |
| ES 热日志 | SSD 热节点 | 7 天 | 秒级 | Kibana/ES DSL | 贵，只放近期 |
| ES 冷日志 | 大容量/冻结索引 | 7-30 天 | 秒-分钟级 | ES 查询/快照恢复 | 中，SSD 换成大容量盘 |
| S3 标准-IA | S3 | 30-90 天 | 秒级 | S3/Athena | 低，可按需查询 |
| S3 Glacier | 归档存储 | 90 天-1 年 | 分钟-小时 | 取回后分析 | 更低 |
| S3 Deep Archive | 冷归档 | 1-2 年 | 小时级 | 极少取回 | 最低 |

### 关键实现点

1. **采集端轮转**：logrotate 按大小轮转本地日志，超限即删，防止节点盘打满。
2. **ES → S3**：日志在 ES 保留到期前，先通过快照（searchable snapshot）或导出到 S3，再删除 ES 索引，避免数据断档。
3. **S3 内分层**：用生命周期规则按天转移（Standard-IA → Glacier → Deep Archive），到期（2 年）自动删除；若合规要求防篡改，可配合对象锁定（Object Lock/WORM）。
4. **合规保证**：保留 2 年不是「一直留着」，而是「到期前不删、到期后必须删」，用规则而非人工保证。
5. **查询降级路径**：近期日志走 ES；归档日志走 S3 + Athena/分析引擎；最老日志走取回，明确各层查询 SLA。

## 七、与阿里云对应

| AWS | 阿里云 |
| --- | --- |
| ES 冷热节点 + ILM | 阿里云 ES 冷热节点 + ILM（同构） |
| S3 Standard-IA / Glacier / Deep Archive | OSS 低频 / 归档 / 冷归档 |
| S3 Lifecycle | OSS 生命周期规则 |
| S3 Object Lock（WORM） | OSS 合规保留策略 |
| Athena 查 S3 | OSS + 外表/DLA（数据分析） |
