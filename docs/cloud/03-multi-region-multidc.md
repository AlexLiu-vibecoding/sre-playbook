# 多地域、多机房部署与运维

> 多地域、多机房节点部署与容灾切换的工程实践，结合阿里云/AWS 实操能力展开。

## 1. 为什么需要多地域/多机房

- 就近接入降低延迟（下载、游戏、内容分发）。
- 单地域/单机房故障时容灾切换。
- 合规要求（数据不出境）。
- 成本与资源可用性（某些规格/资源仅在部分地域）。

## 2. 设计模型

### 同城双活（多可用区）

- 同地域多 AZ，低延迟互联，数据库主备/双写。
- 应用多副本 + 负载均衡自动摘除故障 AZ。

### 异地多活/主备

- 异地机房数据复制（跨地域复制：OSS/S3 复制、数据库异地灾备）。
- 流量调度：DNS 就近 + 故障切换；严重故障时切到备用地域。
- 注意：异地双写数据一致性复杂，多数场景「主备 + 快速切换」更现实。

### 三级架构示例

```text
用户 → DNS/GTM（就近调度）
  ├─ 地域 A（主）：边缘节点 + 中心节点 + 源站副本
  ├─ 地域 B（备）：同上，数据跨地域复制
  └─ 中心管控：配置同步、监控、调度决策
```

## 3. 关键机制

### 数据同步

- 对象存储跨地域复制（OSS 跨区域复制 / S3 CRR）。
- 数据库：跨地域只读副本（RDS 异地灾备）或自建复制；故障时提升。
- 配置/元数据：多地域推送（配置中心 + 一致性校验）。

### 流量调度

- DNS 调度：地域解析 + TTL 控制 + 健康检查自动摘除。
- 全局负载均衡（GTM / Route 53 故障转移 / 阿里云全局流量管理）。
- 调度切换要**可验证、可回切**：每次切换演练都记录步骤与结果。

### 配置与发布一致性

- 多地域发布工具：同一版本分发到各地域，灰度顺序（先小地域后大地域）。
- 配置差异最小化：尽量同一套配置，地域差异收敛到调度层。

## 4. 容灾演练

```text
1. 定义 RTO（恢复时间目标）与 RPO（数据丢失容忍）
2. 场景：单地域故障、单节点故障、DNS 故障、数据复制中断
3. 演练：定期（季度/半年）真实切换，记录时间与问题
4. 改进：每次演练输出改进项
```

## 5. 成本与运维注意

- 多地域成本翻倍（实例、带宽、数据复制），按业务重要度分级部署。
- 监控要「全局视角 + 地域视角」：全局可用性 + 单地域健康。
- 告警按地域归属，避免地域故障告警风暴。
- 配置、密钥、证书多地域同步管理。
