# On-call、变更管理与故障复盘机制

> 作为方向 Owner，稳定性机制建设：On-call、变更管理、故障复盘。本文给出机制设计与落地模板。

## 1. On-call 机制

### 设计目标

- 任何时间有明确的人响应；响应人不孤独（有升级路径）。
- 一线专注止血，二线提供深度支持。
- 记录完整，事后可复盘。

### 轮值设计

```text
一线：轮值工程师（按周/按天轮换），负责响应与止血
二线：对应方向 Owner/资深工程师，负责疑难与根因
升级路径：一线 → 二线 → 值班经理/总监
```

### On-call 工具链

- 告警接收：Alertmanager → 值班群/电话。
- 值班日历：排班表 + 自动同步。
- 值班手册（Runbook）：每个常见告警有处置步骤。
- 交接：交接记录（遗留问题、未处理告警、变更计划）。

### 值班质量指标

- 响应时间（MTTA）、恢复时间（MTTR）。
- 误报率、漏报率。
- 值班期间告警处理完成率。

## 2. 变更管理

### 变更分级

| 级别 | 示例 | 流程 |
| --- | --- | --- |
| 低风险 | 配置优化、监控调整 | 记录 + 当日评审 |
| 中风险 | 组件升级、参数变更 | 评审 + 窗口 + 回滚预案 |
| 高风险 | 架构变更、核心链路发布 | 专项评审 + 演练 + 双人复核 + 审批 |

### 变更流程

```text
提出变更（描述、影响面、回滚方案）
  → 评审（技术正确性、风险、依赖）
  → 审批（按级别）
  → 窗口执行（避开业务高峰）
  → 验证（指标回归）
  → 关闭（记录结果）
```

### 变更纪律

- 变更必须有回滚方案，无回滚不发布。
- 变更分批、可灰度。
- 变更后 24-48h 观察期（指标对比）。
- 重大变更避开高峰与节假日；必要时报备。
- **事后对照**：出现故障先查「最近的变更」——这是最高频根因。

## 3. 故障复盘（Postmortem / RCA）

### 复盘原则

- 不追责个人，追责系统缺陷（Blameless）。
- 事实时间线为纲，杜绝「我认为」。
- 根因分两层：直接原因（技术）+ 深层原因（流程/监控/设计）。
- 每个改进项要有负责人与截止时间，并有验收。

### 复盘报告模板

```markdown
# 故障复盘：<标题>

## 摘要
- 时间：<开始-结束>
- 级别：P0/P1/P2
- 影响：<业务/用户/指标>

## 时间线
| 时间 | 事件 |
| --- | --- |

## 根因分析
- 直接原因：
- 深层原因（监控缺失/变更管理/容量/设计）：

## 止损动作
1.

## 改进项
| 改进项 | 负责人 | 截止 | 状态 |
| --- | --- | --- | --- |

## 遗留风险
```

### 复盘会后动作

1. 改进项录入跟踪系统，周会跟进。
2. 更新 Runbook 与告警（同类问题不再靠人肉发现）。
3. 演练验证改进（注入同类故障）。
4. 同类风险横向排查（不只修单点）。

## 4. 稳定性规划（Owner 视角）

```text
目标：把稳定性做成可度量、可持续的体系
1. 度量：定义 SLI/SLO，建立基线
2. 机制：On-call、变更、复盘、巡检、演练
3. 能力：监控告警、容量、自动化、文档
4. 落地：季度规划 → 月度复盘 → 持续改进
```
