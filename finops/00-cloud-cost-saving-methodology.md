# 云成本节省方法论（Cost Saving Methodology）

> 基于一次 AWS 云成本优化项目的完整实践（四阶段：数据完善 → 方案细化 → 措施落地 → 监控复盘）沉淀而成，并吸收成本分析产品的方法论（口径统一、波动归因、预算预警、标签分账、K8s 核算、折扣核查），可复用于云上计算、数据库、缓存、存储、容器、监控等资源的成本治理。

## 一、核心原则

1. **数据驱动**：先有账单与利用率数据，再谈优化；所有结论基于数据，不凭感觉。分析前先统一成本口径（应付/实付/分摊、同期环比），口径不同结论可能相反。
2. **按占比与潜力排序**：集中火力在高占比、高优化潜力的资源上，避免在低占比项目上花大力气。
3. **业务优先**：优化不牺牲业务稳定性；资源按核心业务、非核心业务、测试环境分层对待。
4. **可逆可控**：每项变更都要有备份、回滚方案与验证步骤。
5. **持续治理**：一次优化不是终点，通过监控、看板与季度复盘持续迭代。

## 二、四阶段方法论

### 阶段 1：成本数据完善

目标：把「一笔糊涂账」变成「一张可决策的成本地图」。

1. **口径统一**：先定义成本口径再分析——应付金额（官网价 - 优惠金额 - 抹零金额）、实际消费（代金券抵用后的现金支付）、消耗金额（按日分摊口径）；环比一律「同期到同日」（月同期环比 / 年同期环比）。
2. **数据聚合**：将语义相近的费用项合并，便于统一分析。例：把 Savings Plans、EC2 实例、EC2-其他合并为「EC2 相关」。
3. **数据过滤**：剔除不可避免的固定支出（如税费），聚焦可优化项。
4. **占比分析**：计算各核心成本项的占比，找出 Top 资源。例：RDS 与 EC2 相关合计占 70%+，即为优化主战场。
5. **波动归因分析**：对两期消费差额做归因，区分实例变动类型（新增/存续/减少）与消费变动类型（用量变化/单价变化），下钻到实例与计费项，回答「这个月为什么涨/降」。
6. **业务归属梳理**：建立「实例 ↔ 业务线」对照表，按核心/非核心/测试分层统计成本；依托云厂商标签做一级/二级部门自动分账（标签即分账基础设施）。
7. **规则化巡检与折扣核查**：预设巡检规则（低利用率、空置节点、异常 POD、过期快照等）定期巡检，异常形成事件并通知负责人；同时对账核查折扣——应付金额 = 官网价 - 优惠金额 - 优惠券抵用 - 抹零，按「无优惠 / 抢占式优惠 / 其他优惠」三类识别应享未享的折扣。
8. **产出**：成本基础分析报告（含各资源占比、波动归因、折扣核查结果、重点优化项选择依据）。

### 阶段 2：降本方案细化

目标：把「可以省钱」变成「每一项都可执行、可测算、可验收」。

1. 按资源类型制定专项策略（见第三节工具箱）。
2. 每项优化措施必须包含：**对象、调整详情、负责人、执行时间、预计节省、风险与备注**。
3. **成本测算**：明确每月节省金额，便于排序与向管理层汇报。
4. **方案评审**：组织业务部门 + 技术部门评审，确认对业务无负面影响。
5. **产出**：整体降本方案（评审版）。

### 阶段 3：降本措施落地

目标：稳、准、快地执行，杜绝「优化出故障」。

1. **排序执行**：低风险、高收益、对业务影响小的项目先做（如非核心启停 → 实例降配 → RI 采购 → 架构迁移）。
2. **窗口与回滚**：变更在业务低峰期执行；执行前备份实例配置/数据，准备回滚方案。
3. **迁移类措施**（Graviton、版本升级）：先做兼容性测试，再试点，最后推广。
4. **全程监控**：执行后持续观察业务指标，确认无负面影响。
5. **产出**：各类执行报告（降配报告、备份配置调整报告、快照清理报告、RI 采购凭证等）。

### 阶段 4：效果监控与复盘

目标：让节省「看得见、守得住、可持续」。

1. **成本看板**：基于 Cost Explorer/账单 + 监控数据搭建看板，每周跟踪成本变化，设置关键指标（综合利用率、环比变动）告警。
2. **预算与预警**：按云平台/付费方式设定预算（月/季/年周期），设置阈值预警，消费达到阈值即触发事件并通知负责人；月度跟踪预算执行，形成行政管控闭环。
3. **前后对比**：对比优化前后的成本数据与业务运行指标，确认降本目标达成且业务未受影响。
4. **季度复盘**：每季度组织复盘，总结优化经验与问题，结合下季度业务规划迭代降本策略；巡检规则随复盘持续更新。
5. **产出**：成本监控看板、周跟踪报告、预算执行报告、季度复盘报告、迭代后的降本策略。

## 三、云资源降本工具箱（按资源类型）

### 1. 计算资源（EC2 / ECS / 虚拟机）

- **业务分层**：核心 / 非核心 / 测试分账，分别采用不同策略。
- **RightSize（降配）**：持续利用率低（如 CPU/内存 < 30%）的实例下调规格；决策前先做**机器画像**（日峰值/晚峰值/平稳），再看 1-3 个月数据（含峰值），不能只看平均值。
- **计费模式**：长期稳定负载（平稳机器）用预留/Savings Plans（或包年包月）；弹性负载（日峰值机器）用按需 + 伸缩；晚峰值/非核心、可中断任务用 Spot。
- **启停策略**：非核心实例配置夜间/节假日自动启停；测试环境自动销毁（如 7 天无活动即清理）。
- **存储**：清理冗余快照；快照生命周期管理；评估 gp3/云盘 IOPS 与吞吐配置是否过度。

计算资源专项子文档：

### 2. 数据库（RDS / 云数据库）

- **备份存储优化**：清理未使用快照；调整备份频率（如全量从 4 小时改为 8 小时）；快照保留策略（如近 3 个月增量 + 1 个年度全量）。
- **版本支持费用**：核查付费扩展支持的实例；能降配的降配，能升版本的上新版本（如 MySQL 5.7 → 8.0），制定迁移路线图，逐步消除支持费。
- **RightSize + RI + 架构迁移三连**：先按利用率降配 → 再为长期实例采购预留（RI）→ 再评估迁移到更高性价比架构（如 Graviton/ARM）。
- **数据治理**：冷数据归档到低成本存储（S3/OSS 低频、归档）；定期清理无效、重复数据；评估非核心实例的 Multi-AZ 是否可转单 AZ。

### 3. 缓存（ElastiCache / Redis）

- **利用率监控**：缓存命中率 < 80%、内存利用率 < 40% 的集群实施降配或减少节点。
- **架构简化**：非核心业务评估单节点替代集群；核心业务合理设置副本数，避免过度冗余。
- **RI 采购**：长期运行（预计 > 6 个月）的节点采购预留；统一容量换算单位（如按 r5.large 折算）核算缺口；根据现金流选择全预付/部分预付/无预付；负载波动大的集群用「预留 + 按需」混合模式。

### 4. 容器（K8s）

- **资源拆分核算**：把资产拆分为 CPU / 内存 / 磁盘三类分别核算；物理资源成本 = 当前资源量 × 月单价（按 30 天估算）。
- **业务分账**：以 Namespace 为业务单元，业务消耗成本 = 分配资源量 × 分摊单价；分摊月单价可调整，作为驱动业务主动优化的经济杠杆。
- **调度与容量**：关注物理资源 → 可分配资源（超卖）的转化现状，识别异常节点与空置节点并及时处理。
- **业务侧优化**：修复异常 POD；调整 CPU/内存申请量（request）；按业务实际消耗缩容。
- **存储优化**：系统盘 / PV / 数据盘三类专项优化（清理、降配、回收）。

### 5. 其他资源

- **OpenSearch / ES**：按索引规模与查询负载下调节点规格与数量；索引生命周期管理（自动删除过期索引、冷索引迁移低成本 tier）。
- **CloudWatch / 监控**：精简指标采集频率与范围；设置日志保留期限；合并重复告警规则。
- **负载均衡（ELB）**：按流量特征选择合适类型（如 ALB 替代 CLB）；配合弹性伸缩在低峰期减少资源。
- **对象存储（S3 / OSS）**：存储类别分层（Standard → IA → Glacier/归档，或用智能分层）；启用生命周期规则；清理冗余与过期数据。

## 四、决策要点（避坑）

1. **先用占比说话**：高占比资源（如 EC2 + RDS 占 70%）才是主战场，低占比资源只做低成本快赢。
2. **RightSize 看真实利用率**：至少 1-3 个月监控数据，覆盖业务峰值；降配后保留扩容预案。
3. **RI/包年包月买前算清**：期限（1/3 年）、付款方式（全预付折扣最高）、容量换算、与实际用量匹配度；买错 RI 等于新浪费。
4. **架构迁移先验证**：Graviton/ARM、数据库大版本升级，必须先兼容性测试 + 试点 + 业务验证。
5. **变更纪律**：低峰执行、先备份、有回滚、执行后监控回归；核心业务变更要评审。
6. **跨云通用映射**：AWS 预留/Savings Plans ≈ 阿里云包年包月/节省计划；Graviton ≈ ARM/倚天实例；S3 分层 ≈ OSS 低频/归档；快照生命周期与成本看板思路完全通用。
7. **先定口径再看数**：应付/实付/分摊、环比口径统一后再做趋势与归因，避免口径混用得出错误结论。
8. **波动先归因再动手**：区分新增/存续/减少与用量/单价变化，确认增长来源后再选优化动作。
9. **机器画像决定计费策略**：按峰值时段分日峰值/晚峰值/平稳机器，分别匹配伸缩/Spot/预留，避免「一刀切」。
10. **预算预警落到事件与通知**：阈值触发后要有事件记录与责任人通知，管控才闭环。
