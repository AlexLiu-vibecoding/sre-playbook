# AI Agent 构建方法

> 内容参考 Anthropic《Building Effective Agents》等公开资料，整理成可落地的构建方法。核心观点：**先工作流，后 Agent；简单优先，复杂只在必要时引入**。

## 1. 什么是 Agent

Agent 没有统一严格定义。工程上把「LLM + 工具 + 记忆」构成的系统统称为 agentic system，但有两种重要区别：

- **工作流（Workflow）**：LLM 和工具通过**预定义的代码路径**编排，流程固定。
- **Agent**：LLM **动态决定**自己的执行过程和工具使用，自主完成任务。

判断标准很简单：**执行路径是否可预测**。

- 流程固定、步骤明确 → 用工作流，可控、稳定、便宜。
- 任务开放、步骤不可预测 → 用 Agent，靠模型决策。

很多所谓「Agent」产品实际是工作流——这没有高下之分，稳定优先。

## 2. 什么时候用（和不用）Agent

### 适合

- 任务需要多步决策，且步骤依赖中间结果（如：代码修复、多源信息调研）。
- 有明确成功标准，可以自动验证（如：测试通过、指标达标）。
- 环境可控、错误可回滚（沙箱、测试环境）。

### 不适合

- 固定流程能解决的问题（先用工作流）。
- 单次 LLM 调用加检索就够的任务。
- 高风险、不可回滚、缺乏验证手段的场景（先加人审）。

> Agent 用「更高的延迟与成本」换「处理开放任务的能力」，这个交易要算得过来。

## 3. 核心组件

### 3.1 模型

- 循环调用 LLM：每次根据上一步的工具结果决定下一步。
- 模型能力决定 Agent 上限：复杂规划、可靠工具调用、错误恢复。

### 3.2 工具（Tool / ACI）

Agent 的能力边界由工具决定。工具设计（Anthropic 称为 Agent-Computer Interface，ACI）是 Agent 工程的核心：

- 工具定义要精确：描述、参数、返回结构。
- 为每个工具写「什么时候用、怎么用、常见坑」。
- 返回结构化结果，错误信息明确可重试。
- 工具越多，模型选择越难——保持精简，按任务分组。
- 幂等与安全：工具可重复执行，权限最小化。

### 3.3 记忆

分层设计：

| 层级 | 内容 | 实现 |
| --- | --- | --- |
| 短期记忆 | 当前对话上下文 | 上下文窗口 |
| 工作记忆 | 任务进度、中间状态 | 结构化状态对象（保存在外部） |
| 长期记忆 | 用户偏好、历史知识 | 向量库/数据库检索 |

要点：

- 记忆要有目的、可审计、可清理（记忆治理）。
- 不要把全部历史塞进上下文——摘要 + 检索。
- 任务状态持久化，支持中断恢复。

### 3.4 规划

常用模式：

- **ReAct**：思考（Reason）→ 行动（Act）→ 观察（Observe），循环直到完成。默认模式。
- **Plan-and-Execute**：先制定计划，再逐步执行；适合多步骤复杂任务。
- **反思（Reflection）**：执行后自我评估、修正再执行。

### 3.5 执行与反馈

- 每步从环境获得**真实反馈**（工具结果、命令输出、测试结果），而不是让模型猜。
- 设置检查点（Checkpoint）与停止条件：最大步数、最大 token/费用、超时。
- 关键决策点让人类确认（Human-in-the-loop）。

## 4. 五种基础工作流模式

| 模式 | 原理 | 适用场景 |
| --- | --- | --- |
| Prompt Chaining | 任务拆成固定顺序步骤，前一步输出进下一步；可加校验门 | 可分解的固定任务（翻译→润色→校对） |
| Routing | 先分类，再路由到专门的处理分支 | 客服分流、简单问题走小模型 |
| Parallelization | 并行处理：Sectioning（拆并行）/ Voting（多次投票） | 独立子任务、需要多角度验证 |
| Orchestrator-Workers | 中央 LLM 动态拆任务、分派给 worker、汇总 | 子任务不可预知（多文件代码修改） |
| Evaluator-Optimizer | 一个生成、一个评估，循环改进 | 有清晰评估标准的迭代任务（翻译、搜索） |

这些模式可以组合。**先选最简单的模式，用评估证明需要再升级。**

## 5. 单 Agent vs 多 Agent

### 单 Agent

- 大多数场景的首选：一个模型带一组工具，简单、便宜、好调试。

### 多 Agent

- 何时拆：角色差异大（规划者/执行者/审核者）、工具集大需要隔离、需要并行。
- 代价：通信成本、上下文重复、错误传播、调试困难。
- 常见形式：Orchestrator-Workers（一个指挥多个工人）、评价循环、流水线协作。

> 经验法则：**先用单 Agent，出现明确的角色/工具/权限隔离需求再拆**。

## 6. 框架与协议

### 框架

| 框架 | 特点 | 适合 |
| --- | --- | --- |
| LangGraph | 有状态图、持久化、可恢复 | 复杂状态工作流 |
| OpenAI Agents SDK | 循环 + Handoff、内置追踪 | 轻量生产 Agent |
| AutoGen / AG2 | 多 Agent 对话协作 | 多角色协作研究 |
| CrewAI | 角色化团队、上手快 | 快速原型 |
| Claude Agent SDK | 深度系统/编码操作 | 编码类 Agent |
| Google ADK | 协议完整 | Google 生态 |

框架是手段不是目的：先用 LLM API 直接实现简单循环，理解底层再决定是否上框架；框架会掩盖 prompt 与响应，调试变难。

### 协议

- **MCP（Model Context Protocol）**：把工具/资源/提示标准化为客户端-服务端模式，一套实现接入多个工具生态。适合做「集成层」。
- **A2A（Agent-to-Agent）**：Agent 之间的通信协议（OpenAI/微软等推动）。

## 7. 生产落地

### 可观测

- Tracing：记录每一步（思考、工具调用、结果、token 成本）。
- 指标：任务成功率、平均步数、工具调用失败率、单任务成本、延迟。
- 日志：输入输出完整留存，可重放调试。

### 评估

- 用**任务级成功率**评估，而不是只看单次回答质量。
- 建回归测试集：典型任务 + 边界 + 失败案例。
- 沙箱环境先跑，验证通过再放宽权限。

### 控制与安全

- 停止条件：最大步数 / 最大费用 / 超时，必须存在。
- 权限：Agent 用最小权限账号；写操作需审批。
- 注入防护：工具输出视为不可信输入，防止被外部内容劫持。
- 数据隔离：多租户场景防止跨用户数据泄漏。
- 人工兜底：关键操作（删除、支付、生产变更）走审批。

### 错误处理

- 工具调用失败：明确错误 → 模型重试/换工具/上报。
- 模型陷入循环：步数上限 + 检测重复动作。
- 输出校验：结构化输出 schema 校验，不合法就重试。

## 8. 运维场景应用（思路参考）

Agent 在 SRE/运维领域的典型形态：

- **故障排查 Agent**：接收告警 → 检索 runbook → 查询指标/日志 → 定位根因 → 输出报告或建议操作。
- **告警分析 Agent**：聚合告警、去噪、生成事件摘要。
- **变更助手**：生成变更计划、检查清单、回滚方案。
- **知识问答**：基于内部文档做 RAG 问答，回答带来源。

共同点：有明确验证手段（指标/命令结果）、工具权限受控、人在关键环节兜底。这类系统建议从「辅助人类」的形态起步，逐步增加自主度。
